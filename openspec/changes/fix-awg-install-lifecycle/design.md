# Design

## Context

`api_install_protocol` использует общий декоратор `serialize_peer_lifecycle`. Тайм-аут допуска (10 с) даёт `peer_lifecycle_busy`; истечение времени ответа (120 с) даёт `peer_lifecycle_still_running`, пока исполнитель продолжает работу под блокировкой. Обработчик возвращает оба кода с одинаковыми HTTP 503 и текстом. Менеджер AWG отводит до 900 с только на ожидание кода выхода сборки. Затем ему ещё предстоит запустить контейнер, настроить и проверить интерфейс.

Окно установки выводит три предполагаемых этапа с интервалом 2 с. Поэтому последний этап и текст 503 из отчёта совместимы с обоими кодами. Если доступны данные исходного запроса, поле JSON `code` различает эти случаи. Строка журнала панели `Lifecycle response deadline reached; worker retains interlock (api_install_protocol)` в момент запроса дополнительно подтверждает истечение срока ответа. Итог операции на конкретном сервере неизвестен.

## Goals / Non-Goals

Сохранить текущий HTTP-контракт для CLI и браузера, ограниченное ожидание входа и защиту исполнителя при отмене запроса. Изменение затрагивает маршрут установки и его представление. Политика блокировок других операций, тайм-ауты команд SSH и политика сборки Docker находятся вне области задачи.

## Decisions

1. Применить существующий режим `@serialize_peer_lifecycle(wait_for_completion=True)` к общему маршруту установки. Этим режимом уже пользуется обновление плагинов AWG. Он снимает ограничение времени ответа для конкретного маршрута, сохраняет очередь, проверку неопределённости, защиту выполняющейся задачи и запись результата до освобождения блокировки. Увеличение глобального лимита затронуло бы остальные операции и оставило бы тот же сбой для более долгих установок.
2. Обрабатывать `err.payload.code` в окне установки. `apiCall` уже передаёт разобранный JSON ошибки. Для `peer_lifecycle_busy` сообщить, что запрос не начал установку и повтор допустим после завершения занятой операции. Для `peer_lifecycle_uncertain` показать необходимость восстановления. Конкретную ошибку установщика, включая текст сборки, вывести как текст. При совместной работе с прежней версией backend трактовать `peer_lifecycle_still_running` как продолжающуюся операцию с неподтверждённым итогом.
3. Пока POST выполняется, показывать неопределённый индикатор. Если браузер потерял соединение или прокси вернул 502/504 без ответа приложения, сообщить о потере результата и предложить проверить целевой экземпляр. При необходимости добавить HTTP-статус к ошибке `apiCall` до разбора тела, сохранив существующие поля. Убрать вывод об успехе из `waitForInstallVisible`: контейнер может появиться до настройки интерфейса, а при переустановке или добавлении экземпляра видимая запись может относиться к прежней установке. Запрос состояния остаётся доступен администратору через обычную проверку сервера.

## Risks / Trade-offs

- Долгий POST может пережить тайм-аут прокси → явно показывать неопределённый результат. Возобновляемое наблюдение за заданием потребовало бы идентификатора операции и отдельного API.
- Настоящая конкуренция за глобальную блокировку сохраняется → после истечения срока допуска запрос завершается без побочных эффектов. Оператор получает основание для безопасной повторной попытки.
- Ошибка конкретного установщика может содержать многострочный вывод → сохранить подробности ответа и безопасное текстовое отображение.

## Migration Plan

Изменения маршрута, окна и переводов поставляются вместе. Формат состояния панели и конфигурация сервера прежние. При откате версии дождаться завершения запущенной установки до перезапуска панели.
