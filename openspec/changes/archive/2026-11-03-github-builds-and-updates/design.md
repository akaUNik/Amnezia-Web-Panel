# Design

## Context

Мотивация и границы — в [proposal.md](proposal.md); поведенческие контракты — в `specs/`.

Наблюдения по текущему checkout:

- `build.yml` запускается на main, `v*` и вручную, собирает три PyInstaller-бинарника, сохраняет `binaries-${runner.os}`, публикует обычный/WARP Docker в GHCR. `release` зависит только от бинарников, сразу публикует три файла через `softprops/action-gh-release`; checksums отсутствуют.
- `test.yml` отдельно выполняет unittest, устанавливает Chromium и выполняет набор root-регрессий с временным состоянием. Его результат не связан зависимостями с публикацией; теговые запуски тестов не предусмотрены.
- `CURRENT_VERSION` в `app.py` равен `v1.8.4`. `checkForUpdates()` в `templates/settings.html` напрямую обращается к GitHub API PRVTPRO, сравнивает строки на неравенство и использует полученные `innerHTML`/`html_url`.
- README и основной Compose используют образы PRVTPRO; WARP override выполняет локальную сборку. `.dockerignore` исключает только `data.json`; бинарные сборки явно включают static/templates/translations.
- `gh repo view` подтвердил публичный `akaUNik/Amnezia-Web-Panel`, default branch `main`. Права Actions и существование/видимость пакета GHCR не проверены. Основные OpenSpec specs пока отсутствуют. В рабочем дереве есть изменения других задач, которые реализация должна сохранить.

## Goals / Non-Goals

**Goals:** связать публикацию с проверками одного SHA; разделить временные файлы запуска и постоянные релизные файлы; дать панели единый источник стабильных обновлений.

**Non-Goals:** ввод нового сервиса обновлений или runtime-токена, автоматическая установка версии, гарантированная побитовая воспроизводимость сборок, сборки macOS, поддержка дополнительных бинарных архитектур. Версии Python сохраняются; по уточнению пользователя установка зависимостей мигрирует на uv с сохранением текущих pins.

## Decisions

### 1. Один граф зависимостей публикации

Сохранить два workflow. Сделать `test.yml` вызываемым через `workflow_call`, сохранив самостоятельные `pull_request` и `workflow_dispatch`. Push main/тегов обслуживает `build.yml`, который вызывает эти же проверки и запускает сборки через `needs`. Удалить самостоятельный push-триггер тестового workflow, чтобы main не запускал одинаковые проверки дважды. Все jobs используют SHA текущего события; схема с независимым `workflow_run` не нужна и усложнила бы привязку результатов к исходникам.

Для PR достаточно полного набора тестов. Push main/`v*` запускает полную сборку. Ручной запуск любого ref имеет режим проверки: бинарные artifacts сохраняются, контейнеры собираются без push, релиз и production-теги не создаются. Публикующие jobs имеют явное условие `github.repository == 'akaUNik/Amnezia-Web-Panel'`, событие push и допустимый ref.

По умолчанию — `contents: read`; `packages: write` только у контейнерных/promotion jobs, `contents: write` только у release job. Использовать `GITHUB_TOKEN`; данные PR не получают публикующих прав. Версии actions проверить по официальным репозиториям на этапе реализации и закрепить совместимые ревизии.

### 2. Явная матрица и идентичность версии

Сохранить существующие имена исполняемых файлов и ресурсы PyInstaller. Зафиксировать runner labels и архитектуру вместо неявного дрейфа `*-latest`:

| Файл | Runner | Архитектура |
|---|---|---|
| `Amnezia-Web-Panel-Linux` | `ubuntu-24.04` | x86_64 |
| `Amnezia-Web-Panel-Windows.exe` | `windows-2022` | x86_64 |

По уточнению пользователя сборки macOS исключены. Распространяются только Linux x86_64 и Windows x86_64; архитектуры указать в README. На каждой ОС smoke-проверка запускает бинарник с временными DATA_FILE/SSH_KNOWN_HOSTS_FILE/TUNNEL_STATE_FILE и проверяет login/static, затем завершает процесс.

Небольшой helper в `scripts/ci/` читает `CURRENT_VERSION` статически, без импорта `app.py`, и на теговых событиях проверяет SemVer и совпадение версии с тегом. Несовпадение останавливает весь публикующий граф до GHCR push. По уточнению пользователя релизные теги с build metadata (`+...`) отклоняются до публикации; SemVer-сравнение в UI продолжает игнорировать metadata. Не подменять версию через runtime env и не маскировать забытый bump автоматической переписью исходников. Main/ручные сборки содержат версию исходников плюс SHA в metadata и не объявляются релизами.

### 3. Actions artifacts и постоянные файлы Releases

Сохранить именованные наборы `binaries-Linux`, `binaries-Windows`; задать `retention-days: 30` и `if-no-files-found: error`. Каждый набор содержит бинарник и собственный metadata-файл с непересекающимся именем: SHA, версия, OS, arch. Скачать в job подготовки только эти два набора текущего запуска. Посторонние `.dockerbuild`/container metadata artifacts не попадают в release assets.

Helper подготовки проверяет состав и принадлежность одному SHA, создаёт общий `build-info.json` и `SHA256SUMS`. Точный комплект релиза: два существующих бинарника и два manifest-файла. Checksums относятся к двум бинарникам и `build-info.json`; сам `SHA256SUMS` в себя не включается. Метаданные включают digest обоих контейнеров и ref/run URL. После скачивания восстановить executable bit Linux; в README описать `chmod +x` при скачивании одиночного файла.

Публиковать сначала draft релиза для точного тега/commit SHA. После загрузки скачать файлы обратно и проверить имена, SHA и checksums, затем снять draft. Использовать GitHub CLI/API с небольшим helper для контролируемой дозагрузки, вместо немедленной публикации action с неявной перезаписью. Существующий совпадающий опубликованный комплект — успешный no-op; конфликт — ошибка. Возобновлять только черновик того же коммита; частично записанный файл черновика допускает замену после проверки, что он не опубликован.

### 4. GHCR и каналы контейнеров

Целевой пакет — `ghcr.io/akaunik/amnezia-panel`; source/revision OCI labels связывают его с репозиторием и SHA. Обычная матрица amd64/arm64 и WARP amd64 сохраняются. QEMU, Buildx и cache `type=gha` остаются; посторонние Docker build record artifacts отключить либо явно исключить из релизного комплекта.

Docker jobs после тестов публикуют уникальные staging-теги по SHA/run attempt для каждого варианта и сохраняют digest в отдельных artifacts. Обновление пользовательских тегов выполняет отдельный promotion job только после успеха обоих вариантов и бинарных сборок, по записанным digest. Ручной запуск выполняет build без входа в GHCR и push. Сборка без push считается проверкой образов; распространяемые образы появляются на успешном push main/версии.

- Main: `main`, `sha-<sha>`, `latest` и варианты `-warp`.
- Стабильный тег: точная `X.Y.Z`, алиасы `X.Y`, `X`, `latest` и соответствующие `-warp`.
- Prerelease: только точная `X.Y.Z-rc.N` и её `-warp`, без стабильных алиасов; GitHub release помечен `prerelease: true`, `make_latest: false`.

Сериализовать публикующие запуски без `cancel-in-progress`, выполнять проверку актуальности main перед продвижением его aliases. Для стабильных тегов не понижать уже опубликованные aliases при выпуске старой поддерживаемой версии: точный тег публикуется всегда, major/minor/latest продвигаются только при увеличении соответствующей версии. Главный GitHub release также не переводить на более старую версию; сверять текущий стабильный релиз перед `make_latest`.

Registry и Releases не дают общей транзакции: после успешных сборок продвижение алиасов и публикация release могут прерваться по сети. Сохранять предыдущие digests и состояние шагов в summary; повтор завершает публикацию, либо оператор возвращает aliases на предыдущие digests. Не обещать атомарность двух вариантов при сетевом отказе самого promotion. Подтвердить публичность пакета анонимным pull после первого push.

### 5. Проверка обновлений остаётся в браузере

Репозиторий публичный, существующий поток уже использует browser fetch. Сохранить эту архитектуру: фиксированный endpoint `https://api.github.com/repos/akaUNik/Amnezia-Web-Panel/releases/latest`, анонимный запрос, timeout 10 секунд через AbortController. Backend proxy и хранение GitHub-токена не требуются. Сетевые ограничения браузера остаются явным состоянием ошибки с ручной ссылкой.

В небольшом модуле констант проекта хранить owner/repository/API/releases URL, передавать значения в settings через Jinja `tojson`; не дублировать endpoint и download URL в шаблоне/JS. `CURRENT_VERSION` остаётся источником версии. Сравнение выделить в тестируемый JS helper: нормализовать необязательный `v`, сравнивать три числовых компонента и prerelease по SemVer, игнорировать build metadata. Некорректный формат означает невозможность сравнения.

Обработать 200, отсутствие стабильного релиза (404 фиксированного публичного endpoint), rate limit/403/429, 5xx, timeout, JSON/schema error. Ответ, помеченный draft/prerelease, отклонить даже при неожиданном контракте `/latest`. Отсутствие стабильного релиза не означает, что установленная версия актуальна. Значения выводить через `textContent`; URL скачивания фиксировать на `/releases`, не доверять произвольному `html_url`. Ручная ссылка видна всегда; завершение запроса всегда восстанавливает кнопку/spinner. Добавить строки всех новых состояний во все пять локалей.

### 6. Установка и документация

Основной Compose переключить на собственный GHCR `latest`. WARP override использует опубликованный `latest-warp` с прежними capabilities, devices и volumes; локальный build вынести в дополнительный `docker-compose.warp.local.yml`, подключаемый последним. Сохранить имена томов и DATA_FILE. README описывает clone собственного репозитория, скачивание Actions artifacts, Releases/checksums, архитектуры, published/local WARP и откат по digest. Исторические упоминания PRVTPRO и независимые сторонние источники сохраняются.

Сузить `.dockerignore`/`.gitignore` для локальных credentials, `.git`, virtualenv, временного состояния и результатов сборки, поскольку Dockerfile использует `COPY . .`. Не исключать ресурсы приложения и необходимые runtime-модули. Проверять содержимое сборочного контекста без вывода секретов.

### 7. Opt-in проверка опубликованного Compose на Linux

По отдельному согласию пользователя от 2026-11-02 `test.yml` получает manual-only job `published-compose`: он включается лишь через `workflow_dispatch` с `qualify_published=true` в основном репозитории. Обычные PR, reusable/main/tag проверки и default manual unit-тесты не выполняют эту дополнительную проверку. Job имеет только `contents: read`, не входит в registry и не выполняет build/push/release.

Helper принимает base container tag и необязательный полный expected SHA, сверяет оба варианта, source/version/platforms и закрепляет digests перед анонимным pull. Оба published Compose запускаются на ubuntu-24.04 с уникальными временными project/volume names и localhost-портами. Проверяются login/static, пересоздание контейнера, сохранение data/fixture-файлов, а у WARP — TUN, CLI и отдельное состояние WARP. В `finally` удаляются только созданные им временные ресурсы; JSON с public metadata/checksums сохраняется как artifact на 30 дней. Это воспроизводимая альтернатива медленной загрузке WARP на локальную машину, без ослабления требований задачи 7.3.

## Risks / Trade-offs

### Уточнение: uv-проект

`pyproject.toml` и `uv.lock` заменяют `requirements.txt`. Приложение остаётся непакетируемым проектом (`package = false`); версия проекта синхронизируется с `CURRENT_VERSION` при релизе. Локальный Python по умолчанию — 3.11 (`.python-version`), минимальный — 3.10, Docker сохраняет Python 3.14 и явно выбирает интерпретатор базового образа. Playwright выделен в dev-группу, PyInstaller — в build-группу; runtime pins сохраняются. CI использует `uv sync --locked`, бинарные сборки — `--no-dev --group build`, Docker — `--no-dev`. Локальный `.venv` исключён из build context. Обновление зависимостей выполняется через uv с коммитом обоих файлов проекта.

- [Лимиты хранения] → 30 дней для Actions проверяются относительно настроек репозитория; релизные файлы не зависят от этого срока. Бинарники не коммитятся в Git. Настройки и команды скачивания описать в `docs/github-ci.md`.
- [GHCR package может быть private или принадлежать ранее созданному пакету] → проверить repository association и доступ `GITHUB_TOKEN`, затем видимость и анонимный pull; дополнительные PAT не встраивать.
- [QEMU/WARP и зависимости ОС могут ломать отдельные сборки] → полная матрица и smoke-проверки на runners; ошибки не обходить удалением платформы. Python 3.11 тестов и Python 3.14 Docker требуют проверки фактических сборок.
- [Ограничения GitHub API у пользователя] → timeout, понятная ошибка, повтор и постоянная ссылка на релизы. Proxy/cache можно рассмотреть отдельным изменением при подтверждённой необходимости.
- [COPY всего checkout] → минимально достаточные ignore-правила и проверка отсутствия локальных файлов состояния/настроек в образе.
- [Проверка CI требует remote запусков] → завершённость YAML или локальных тестов не равна успешной публикации; сохранять URL run, checksums и manifests в отчёте проверки реализации.

## Migration Plan

1. После отдельного apply реализовать helpers, workflows и UI, выполнить локальные проверки, затем доставить изменения штатным GitHub PR-процессом.
2. Проверить Actions/package permissions и лимит хранения. Выполнить ручной verification-запуск без публикации; скачать два бинарника и проверить запуск на соответствующих ОС.
3. После попадания в main проверить автоматический pipeline и анонимный pull обоих образов, manifests, источник обновлений и Compose на временном томе.
4. На следующем согласованном версионном теге с обновлённым `CURRENT_VERSION` проверить полный release, обратное скачивание файлов/checksums и повтор запуска. Не создавать фиктивный стабильный релиз ради проверки; prerelease использовать для проверки тегового пути без смены стабильного канала.
5. При отказе вернуть опубликованные aliases на записанные предыдущие digests; полный релиз не переписывать, неполный draft завершить повтором. Откат конфигурации/образа не удаляет volumes.
